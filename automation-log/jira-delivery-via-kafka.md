## 2026-10-27 (ограничение: тесты не parallel-safe)

### Находка

Все Jira-тесты (TC-011, TC-013/014/015, TC-007/012, `test_create_entry_logs_to_jira`,
`test_jira_connection_is_configured_and_reachable`) бьют в одну и ту же задачу `KAN-1`
(`test_task`/`task_prefix`+`task_number=1`). Их корректность держится на двух неявных условиях,
которые сейчас выполняются только потому, что pytest прогоняется строго последовательно
(`pytest -m "not db"`, без `-n`; `pytest-xdist` не в `requirements.txt`):

- **Позитивные тесты (TC-011)** ищут "свой" worklog через `_matching_worklog()` — берут
  **последний** worklog задачи и проверяют, что его `comment` содержит переданное описание. Если
  между созданием записи и опросом в Jira параллельно идущий тест добавит свой worklog, он станет
  "последним", совпадение не найдётся → ложный fail по таймауту, хотя доставка прошла нормально.
- **Негативные тесты (TC-013/014/015)** сравнивают `id` последнего worklog до и после создания
  записи — ждут, что он **не изменится**. Если параллельно идущий тест добавит worklog в тот же
  промежуток, `id` изменится → ложный fail, хотя сам проверяемый сценарий ("наша" запись не
  долетела) на самом деле верен.
- **Lag-проверка (`wait_for_zero_lag`, группа E)** тоже не привязана к конкретному сообщению — она
  подтверждает "у консьюмер-группы нет бэклога прямо сейчас", а не "обработано именно моё
  сообщение". При нескольких сообщениях в очереди одновременно это ещё один канал ложных
  срабатываний в обе стороны.

### Последствие

Тесты корректны **только при последовательном прогоне** и только пока все делят одну задачу
`KAN-1`. Для параллелизации (`pytest-xdist` или параллельные job'ы в Jenkins) понадобится одно из:
- развести Jira-тесты по разным задачам (`KAN-1`, `KAN-2`, ...);
- переписать идентификацию "своего" worklog на уникальный маркер по всем worklogs задачи, а не
  только по последнему;
- сериализовать именно Jira/Kafka-тесты (`--dist=loadgroup` в `pytest-xdist` или аналог), оставив
  параллельность только тестам, не трогающим Jira.

Не баг — pytest и так прогоняется последовательно, прогоны в Jenkins это подтверждают. Зафиксировано
как known limitation, не как TODO с приоритетом: явного решения, что с этим делать, пока не
принято.

`{"code":4002,"message":"Not supported"}` независимо от параметров. Рабочий эндпоинт —
**`/messages/v2`**, SSE-поток (`data: {...}` построчно, события `PHASE`/`CONSUMING`/`MESSAGE`/`DONE`).
С параметрами `mode=LATEST&limit=1` отдаёт ровно последнее сообщение партиции без необходимости
фильтровать по содержимому — проверено живым запросом из контейнера Jenkins, получил своё же
тестовое сообщение с полным payload'ом (`entry_id`/`task`/`time_spent`/`date`/`description`).

Добавлен `KafkaUiApi.get_latest_message(topic)` — парсит SSE построчно, ищет событие `type=="MESSAGE"`,
возвращает распарсенный JSON из `message.value`.

## 2026-10-28 (TC-001: проверка отсутствия в других топиках)

### Контекст

Пользователь планирует масштабирование — появятся новые топики. Вопрос: проверяет ли TC-001, что
запись лежит именно в правильном топике, а не просачивается в другие? До этой правки — нет: тест
читал только жёстко заданный `jira-worklog-requests` и ничего не знал о существовании других
топиков в принципе.

### Изменение

Добавлены `KafkaUiApi.list_topics()` (все пользовательские, не internal, топики кластера),
`get_latest_messages(topic, limit)` (обобщение `get_latest_message` на список; сообщения с
непарсящимся как JSON value пропускаются, а не роняют вызов — на будущих топиках схема может быть
другой) и `assert_entry_absent_from_other_topics(entry_id, exclude_topic, scan_limit=50)` — сканирует
последние `scan_limit` сообщений каждого топика кластера, кроме исключённого, и падает, если
`entry_id` найден где-то ещё. В `test_published_message_matches_confirmed_entry` (TC-001) добавлен
шаг, вызывающий эту проверку после сравнения содержимого.

**Важная честная оговорка:** сейчас в кластере только один пользовательский топик
(`jira-worklog-requests`), поэтому этот новый шаг **проходит вхолостую** — `list_topics()` после
исключения `jira-worklog-requests` возвращает пустой список, сравнивать не с чем. Логику обнаружения
проверил отдельно (не через pytest, вручную): вызвал `assert_entry_absent_from_other_topics` с
`exclude_topic`, НЕ совпадающим с реальным топиком записи — метод корректно нашёл совпадение и
бросил `AssertionError`. Это подтверждает, что механизм рабочий, а не то, что он сейчас что-то
реально отсеивает в проде — реальная польза появится только когда добавятся другие топики.

Полный прогон: 13 тестов (без db), все зелёные, 24.10с.

## 2026-10-28 (маркер chaos)

### Решение

Оставшиеся неавтоматизированные TC (TC-003/004/005/008/016) требуют останавливать/пересоздавать
общие контейнеры или менять `.env` окружения — это ломает среду для всех (Jenkins и локальной
работы одновременно), поэтому для них никогда не будет безопасного автоматического прогона в
текущем Jenkins. Решили явно завести для них маркер `chaos` и исключить из агрегированной
категории `all`, а не оставлять эти TC просто "не автоматизированными" без механизма — так в
будущем, когда тесты под этот маркер появятся, они не будут давать Jenkins ложный fail по причинам,
не относящимся к самому тесту.

**TC-009/TC-010 отдельно не попадают под `chaos`** — они технически триггерятся чистым HTTP без
контейнеров (`task="/"` даёт от Jira HTTP 405, не 404 — обнаружено в предыдущем заходе), но
навечно поражают единственный partition топика для всех последующих тестов (нет способа снять
блокировку без admin-доступа к Kafka, которого нет). Эти TC не реализованы вообще, не помечены
`chaos` — решение по ним отдельное и пока не принято (нужна либо изоляция под chaos-тесты, либо
admin-эндпоинт в vinnie-assistant).

### Изменения

- `pytest.ini`: новый маркер `chaos` — "тесты, требующие останавливать/пересоздавать контейнеры
  или менять .env окружения — только ручной/local-only прогон, не в Jenkins".
- `Jenkinsfile`: `all` теперь `pytest -m "not db and not chaos"` (было `not db`).

Самих chaos-тестов пока не написано — это только инфраструктура (маркер + исключение), чтобы
будущие TC-003/004/005/008/016 можно было реализовать без риска сломать Jenkins.

### Находки (эмпирическая проверка реального Jira API, не предположения)

## 2026-10-28 (TC-011: проверка started == отправленной дате)

проверка `started == entry_date` была бы слабой: откат `jira_client.log_work()` на `started =
сегодня` при сбое парсинга (сам механизм бага KAN-4) совпал бы с ожиданием случайно, не поймав
регрессию.

`test_entry_worklog_appears_in_jira` (TC-011):
