## 2026-10-27 (ограничение: тесты не parallel-safe)

### Находка

Все Jira-тесты (TC-011, TC-013/014/015, TC-007/012, `test_create_entry_logs_to_jira`,
`test_jira_connection_is_configured_and_reachable`) бьют в одну и ту же задачу `KAN-1`
(`test_task`/`task_prefix`+`task_number=1`). Их корректность держится на двух неявных условиях,
которые сейчас выполняются только потому, что pytest прогоняется строго последовательно
(`pytest -m "not db"`, без `-n`; `pytest-xdist` не в `requirements.txt`):

- **Позитивные тесты (TC-011)** ищут "свой" worklog через `_matching_worklog()` — берут
  **последний** worklog задачи и проверяют, что его `comment` содержит переданное описание. Если
  между созданием записи и опросом в Jira параллельно идущий тест добавит свой worklog, он станет
  "последним", совпадение не найдётся → ложный fail по таймауту, хотя доставка прошла нормально.
- **Негативные тесты (TC-013/014/015)** сравнивают `id` последнего worklog до и после создания
  записи — ждут, что он **не изменится**. Если параллельно идущий тест добавит worklog в тот же
  промежуток, `id` изменится → ложный fail, хотя сам проверяемый сценарий ("наша" запись не
  долетела) на самом деле верен.
- **Lag-проверка (`wait_for_zero_lag`, группа E)** тоже не привязана к конкретному сообщению — она
  подтверждает "у консьюмер-группы нет бэклога прямо сейчас", а не "обработано именно моё
  сообщение". При нескольких сообщениях в очереди одновременно это ещё один канал ложных
  срабатываний в обе стороны.

### Последствие

Тесты корректны **только при последовательном прогоне** и только пока все делят одну задачу
`KAN-1`. Для параллелизации (`pytest-xdist` или параллельные job'ы в Jenkins) понадобится одно из:
- развести Jira-тесты по разным задачам (`KAN-1`, `KAN-2`, ...);
- переписать идентификацию "своего" worklog на уникальный маркер по всем worklogs задачи, а не
  только по последнему;
- сериализовать именно Jira/Kafka-тесты (`--dist=loadgroup` в `pytest-xdist` или аналог), оставив
  параллельность только тестам, не трогающим Jira.

Не баг — pytest и так прогоняется последовательно, прогоны в Jenkins это подтверждают. Зафиксировано
как known limitation, не как TODO с приоритетом: явного решения, что с этим делать, пока не
принято.

### Находка: `find_issue()` не обрабатывает статусы кроме 200/404

## 2026-10-28 — флейк в Jenkins (DNS Docker Desktop, не баг приложения)

### Контекст

После пуша KAN-5 прогоны в Jenkins (build #150, #151, #152) и локальные перезапуски стали
нестабильно падать на разных кейсах `TestJiraWorklogDelivery::test_entry_worklog_appears_in_jira`
(то `task_1`, то `task_1_second`, то `task_1_day_unit`/`task_1_yesterday` — каждый раз другой) и
один раз на `test_jira_connection_is_configured_and_reachable`. Все падения — `assert None is not
None` (воркалог не появился за 30с) либо напрямую `requests.exceptions.ConnectionError`.

### Находка

В логах `vinnie-assistant-jira-consumer-1` за те же окна — повторяющийся
`NameResolutionError` при обращении к `iyk040190-1790711247004.atlassian.net`:

```
[ERROR] Entry #NNNN: find_issue error, will retry: HTTPSConnectionPool(host='iyk040190-...atlassian.net', port=443):
Max retries exceeded ... NameResolutionError("...Failed to resolve ... Temporary failure in name resolution")
```

Прямая проверка резолвинга изнутри контейнеров (`vinnie`, `jira-consumer`) дала ~20-27% провалов
на повторных попытках (`socket.gethostbyname`), при этом резолвинг с хоста (macOS, резолверы
`1.1.1.1`/`8.8.8.8`) — 10/10 успешных, без единого сбоя. Рестарт Docker Desktop (не только
контейнеров) проблему не убрал — сбои продолжились в тех же логах после рестарта.

**Решающая проверка**: откатили `backend/app` в `vinnie-assistant` на коммит d5f2216 (до фикса
KAN-5) и `tests/`/`utils`/`pytest.ini` в `vinnie-tests` на коммит 381b5ef (до регрешн-теста
KAN-5), перезапустили `vinnie`/`jira-consumer` с этим кодом и прогнали тот же набор тестов.
**Результат идентичен**: 3 из 16 тестов упали по той же причине, и в логах консьюмера — те же
`NameResolutionError` в то же окно времени. Это исключает любую связь с кодом/коммитами KAN-4/
KAN-5 — ни один из них не трогает сеть/DNS. Причина — встроенный DNS-proxy Docker Desktop
(VM-слой `linuxkit`/`vpnkit`), нестабильный на этой машине независимо от кода проекта.

Оба репозитория возвращены на `main`, контейнеры перезапущены с актуальным кодом.

### Решение

Фиксить саму VM Docker Desktop из кода проекта невозможно — сделали тесты устойчивыми к
кратковременным сетевым сбоям вместо того, чтобы полагаться на стабильность DNS:

- `tests/api/test_jira_integration.py::test_entry_worklog_appears_in_jira` — `wait_until` для
  появления воркалога: `timeout=30` → `60`; следующий `wait_for_zero_lag` в том же тесте:
  `timeout=10` → `20`.
- `tests/api/test_jira_integration.py::test_invalid_entry_does_not_appear_in_jira` —
  `wait_for_zero_lag`: `timeout=30` → `60`.
- `tests/api/test_jira_sync.py::test_nonexistent_task_returns_not_found` и
  `test_malformed_task_key_does_not_retry_forever` — `wait_for_zero_lag`: `timeout=30` → `60`.
- `tests/api/test_jira_sync.py::test_jira_connection_is_configured_and_reachable` — этот вызов
  синхронный (без Kafka, без своего ретрая), один сетевой сбой валил тест сразу. Обёрнут в
  `wait_until(..., timeout=15, interval=5)` — до 3 повторных попыток вызова
  `check_jira_connection`, ждём именно `status == 200`, не просто ответ.

Это не устраняет причину (нестабильность Docker Desktop), а не даёт короткому DNS-сбою красить
весь прогон Jenkins тестом, который не нашёл реального дефекта.

### Прогон

`tests/api/test_jira_sync.py` — 5 passed. `tests/api/test_jira_integration.py` — 12 passed.
Полный набор (`-m "not db and not chaos"`) — **28 passed** (без изменений в числе тестов,
только в таймаутах).

## 2026-10-28 (продолжение) — та же проблема вернулась в build #153, донастроили таймауты

### Контекст

После пуша мер из предыдущей секции build #153 всё равно упал — на этот раз на
`test_invalid_entry_does_not_appear_in_jira[negative_time_spent]` (lag не вернулся к 0 за
60с) и `test_jira_connection_reports_not_found_for_nonexistent_task` (`status == None` вместо
404, та же `NameResolutionError`).

### Находка

Два отдельных пробела:

1. **Пропущенный тест**: retry-обёртку на прошлом шаге добавили только в
   `test_jira_connection_is_configured_and_reachable` (ждёт 200), но забыли про точно такой же
   незащищённый синхронный вызов в `test_jira_connection_reports_not_found_for_nonexistent_task`
   (ждёт 404) — тот вызывает тот же `check_jira_connection` без единого ретрая.
2. **DNS-сбои идут кластерами**: в логах `jira-consumer` за время прогона — 2-3
   `NameResolutionError` подряд на одну и ту же запись (Entry #1357: 14:07:25 → 14:07:44 →
   14:07:57, итог ~49с на одну запись). Это Kafka-очередь с одним консьюмером на партицию —
   застрявшая запись блокирует все последующие в очереди. Поэтому `timeout=60` в конкретном
   тесте не всегда достаточно: лаг не упадёт к 0, пока не разрулится именно блокирующая запись,
   независимо от таймаута более поздних тестов.

### Решение

Обсудили с пользователем: причину (нестабильность Docker Desktop) из кода не починить,
дальнейшее увеличение таймаутов — осознанный временный костыль с понятным пределом
полезности (при совсем плохом кластере DNS-сбоев не поможет и это). Пользователь подтвердил
этот путь.

- `tests/api/test_jira_sync.py::test_jira_connection_reports_not_found_for_nonexistent_task` —
  обёрнут в тот же `wait_until`-retry, что и `test_jira_connection_is_configured_and_reachable`
  (ждём именно `status == 404`, не просто ответ).
- Таймауты подняты ещё раз:
  - `test_entry_worklog_appears_in_jira`: `wait_until` на появление воркалога `60` → `90`;
    последующий `wait_for_zero_lag` в том же тесте `20` → `30`.
  - `test_invalid_entry_does_not_appear_in_jira`: `wait_for_zero_lag` `60` → `90`.
  - `test_nonexistent_task_returns_not_found`, `test_malformed_task_key_does_not_retry_forever`:
    `wait_for_zero_lag` `60` → `90`.
  - `test_jira_connection_is_configured_and_reachable`,
    `test_jira_connection_reports_not_found_for_nonexistent_task`: синхронный retry
    `timeout=15, interval=5` (3 попытки) → `timeout=30, interval=5` (6 попыток).

### Прогон

`tests/api/test_jira_sync.py` — 5 passed (42.4с). `tests/api/test_jira_integration.py` —
12 passed (184.7с, включая ранее упавший `negative_time_spent`).
