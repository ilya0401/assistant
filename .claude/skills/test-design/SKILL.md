# Тест-дизайн

## Когда НЕ использовать этот скилл

Если требований ещё нет или они не проверены — вернись к **requirements-writer**/**requirements-reviewer**, не дизайнь тесты на сырых требованиях. Этот скилл отвечает за дизайн проверок (что и зачем тестировать), а не за реализацию автотеста — написание кода Playwright/pytest под готовый тест-кейс это отдельный шаг после этого скилла, не часть его.

Требования для vinnie хранятся в `vinnie-assistant/requirements/<слаг-фичи>.md` (см. requirements-writer). Если пользователь дал только REQ-ID или название фичи, а не текст требований — найди соответствующий файл там перед тем как выводить тесты.

## Откуда берутся проверки

Не выдумывай тест-кейсы "из головы" по ощущению — выводи их из требований через конкретные техники тест-дизайна. Это не формальность: техника определяет, какие именно проверки ты не забудешь.

Прежде чем писать шаги теста, сформулируй **оракул** — то, по чему однозначно определяется "прошёл/не прошёл" (конкретное значение в БД, текст на экране, HTTP-статус). Если оракул не формулируется однозначно — вероятно, само требование непроверяемо, и это повод вернуться к requirements-reviewer, а не придумывать расплывчатый тест-кейс.

| Техника | Когда применять | Что даёт |
|---|---|---|
| **Эквивалентные классы** | Есть входной параметр с диапазоном/набором допустимых значений | Группирует бесконечное число входов в несколько представительных классов — не нужно перебирать всё |
| **Граничные значения** | То же самое, но именно на границах чаще всего баги | Проверки на границе класса и сразу за ней (min-1, min, min+1, max-1, max, max+1) |
| **Таблица решений** | Поведение зависит от комбинации нескольких условий | Не пропустить комбинацию условий, которую легко упустить при линейном переборе |
| **Переходы состояний** | У сущности есть жизненный цикл/статусы | Проверки на допустимые и недопустимые переходы между состояниями |
| **Исследовательское/error guessing** | Всё перечисленное выше покрыто, остался "чуйка"-слой | Ловит то, что систематические техники не предсказывают — опечатки, гонки, нестандартный пользовательский ввод |

Для каждого `REQ-XXX` явно укажи, какой техникой выведен каждый тест-кейс — это не бюрократия, а способ самому не забыть покрыть граничные/негативные случаи, которые обычно теряются при интуитивном подходе (если вы уже используете у себя эту привычку — так и продолжайте, она работает).

## Приоритизация — риск, не интуиция

Приоритет = **вероятность** (насколько вероятно, что здесь баг) × **влияние** (насколько плохо, если баг проскочит в прод).

| Приоритет | Пример |
|---|---|
| **Critical** | Высокое влияние + высокая вероятность — потеря данных пользователя, сломанный основной сценарий |
| **High** | Высокое влияние ИЛИ высокая вероятность, не оба сразу |
| **Medium** | Второстепенный сценарий, есть обходной путь |
| **Low** | Косметика, крайне маловероятный edge case |

Если у проекта уже есть своя шкала приоритетов (например, в Jira/TestRail) — используй её вместо этой, не навязывай свою поверх существующей конвенции.

Приоритет (важность для бизнеса) и риск (вероятность бага) иногда расходятся — например, малоприоритетная фича может быть технически хрупкой. Если видишь такое расхождение, отметь оба тега отдельно, а не сворачивай в одно число: это подсказка, что низкоприоритетный сценарий всё равно стоит покрыть из-за риска.

## Порядок вывода — сначала smoke, затем позитив, затем негатив

Когда выводишь набор тест-кейсов/чек-лист (не один-единственный тест-кейс, а пул на фичу/REQ-область) — группируй их крупными блоками в этом порядке, а не перемешивай вперемешку по мере того, как придумал:

1. **Smoke** — по одному "счастливому" прогону на каждую основную функцию из области, подтверждающему, что фича вообще работает end-to-end. Если smoke не проходит, тратить время на остальное бессмысленно.
2. **Позитивные сценарии** — корректные входы за пределами одного happy path из smoke: другие валидные классы эквивалентности, другие валидные комбинации в таблице решений, альтернативные допустимые переходы состояний.
3. **Негативные/граничные сценарии** — невалидный ввод, отказы зависимостей (брокер/внешний API недоступен, протухший токен), граничные значения, error guessing.

Внутри каждого блока тест-кейсы всё равно сортируются по приоритету/риску (см. ниже) — порядок блоков не заменяет приоритизацию, а задаёт читателю возрастающую детализацию сверху вниз: "фича жива" → "работает правильно на валидных входах" → "не ломается на невалидных". Это также помогает заметить дыру в покрытии — например, если у REQ-области вообще нет негативного блока.

Отметь явным подзаголовком (`#### Smoke`, `#### Позитивные`, `#### Негативные`) каждый блок — независимо от того, в тест-кейсы, чек-лист или тест-план в итоге оформляется результат.

## Кандидат на автоматизацию

Для каждого тест-кейса помечай, стоит ли его автоматизировать: стабильный ли сценарий (не будет часто меняться), насколько он ценен при повторных прогонах (регрессия, а не одноразовая проверка), и насколько он вообще автоматизируем (не требует, например, ручной визуальной оценки "красиво ли"). Разовая ручная проверка редкого edge case обычно не стоит стоимости автоматизации — явно скажи "нет, вручную" и почему, а не автоматизируй всё подряд по умолчанию.

## Формат вывода — спроси, если не очевидно из контекста

Три формата закрывают разные задачи — не производи все три по умолчанию, уточни, какой нужен:

**Тест-кейсы** — когда нужна воспроизводимая пошаговая проверка (ручное тестирование, онбординг нового тестировщика, формальная приёмка). Блоки smoke/позитив/негатив из раздела выше оформляются подзаголовками над соответствующими строками таблицы:
```markdown
#### Smoke
| ID | Требование | Предусловия | Шаги | Ожидаемый результат (оракул) | Приоритет | Риск | Техника | Автоматизация |
|----|-----------|-------------|------|---------------------|-----------|------|---------|----------------|
| TC-001 | REQ-STORE-001 | Backend и Postgres запущены | 1. Сказать корректную команду целиком 2. Подтвердить | Запись сохраняется в Postgres с правильными полями | Critical | High | — (happy path) | Да |

#### Позитивные
| TC-002 | REQ-PARSE-001 | ... | ... | Другой валидный формат даты распознаётся так же корректно | High | Medium | Эквивалентный класс (валидные форматы даты) | Да |

#### Негативные
| TC-003 | REQ-PARSE-002 | Микрофон доступен, backend запущен | 1. Сказать "задача без времени" 2. Отправить на распознавание | Система запрашивает уточнение времени, не сохраняет запись | Critical | High | Эквивалентный класс (неполный ввод) | Да — стабильный сценарий, частая регрессия |
```
Если тест-кейсы пойдут в инструмент вроде TestRail/Jira — предложи вывод в CSV вместо markdown-таблицы, так их проще импортировать.

**Чек-лист** — когда нужна быстрая проверка перед релизом/смоук-тест, шаги не нужны, важна скорость прохода. Здесь уровни (smoke/sanity/regression) — это **другая ось группировки**, не та же самая: она не про порядок позитив/негатив внутри дизайна, а про то, когда этот набор прогоняют (перед релизом / после мелкого фикса / полная регрессия). Внутри каждого уровня всё равно применяй порядок smoke-функциональности → позитив → негатив из раздела выше:
```markdown
### Smoke
- [ ] (Critical) Корректный ввод → запись сохраняется в Postgres с правильными полями — REQ-STORE-001
- [ ] (Critical) Неполный голосовой ввод → запрашивается уточнение, запись не сохраняется — REQ-PARSE-002
```

**Тест-план** — когда нужен верхнеуровневый документ для согласования со стейкхолдерами, а не исполняемые проверки:
```markdown
## Тест-план: <фича>
- Цели и объём тестирования
- Что в scope / что явно out of scope
- Стратегия (какие техники, ручное/авто, окружения)
- Критерии входа/выхода (entry/exit criteria)
- Риски и как они влияют на приоритизацию (см. выше)
- Ресурсы и сроки
```

## Куда сохранять

Тест-кейсы — отдельный артефакт от требований, даже если выведены из одного REQ-файла: требования и тест-кейсы живут параллельно, не в одной папке, чтобы можно было найти/обновить нужное отдельно. Тест-кейсы логически принадлежат репозиторию с тестами, а не продуктовому репозиторию — но держи их заодно и в `vinnie-assistant`, рядом с требованиями, чтобы пара была видна без переключения между проектами. Поэтому сохраняй **в оба репозитория** (это соседние директории на одном уровне — `vinnie-assistant/` и `vinnie-tests/`), идентичный файл в обоих:

```
vinnie-assistant/test-cases/<слаг>.<md|csv|xlsx>   — рядом с requirements/<слаг>.md, для видимости пары
vinnie-tests/test-cases/<слаг>.<md|csv|xlsx>       — канонический дом: здесь живут тесты и будущая автоматизация
```

Используй **тот же слаг**, что у соответствующего файла в `requirements/<слаг>.md` в `vinnie-assistant` — так пара "требования ↔ тест-кейсы" находится по имени файла без необходимости лезть в содержимое. Расширение — по формату вывода (markdown-таблица/чек-лист/план → `.md`; просили CSV для TestRail/Jira → `.csv`; просили Excel → `.xlsx`).

Если `vinnie-tests` не найден по соседству (другая машина/окружение) — сохрани хотя бы в `vinnie-assistant/test-cases/` и явно скажи пользователю, что копия в тестовый репозиторий не создана.

Перед созданием нового файла проверь в обоих репозиториях, нет ли уже файла с таким слагом — если есть, скорее всего нужно дополнить его, а не плодить дубликат.

## Перед тем как отдать результат — самопроверка

- Каждый тест-кейс/пункт чек-листа ссылается на конкретный REQ-ID?
- У каждого есть однозначный оракул, а не расплывчатое "работает корректно"?
- Приоритет и риск расставлены по логике "вероятность × влияние", а не по ощущению?
- Указано, кандидат ли тест-кейс на автоматизацию, и почему?
- Покрыты не только позитивные, но и негативные/граничные сценарии для каждого REQ?
- Вывод сгруппирован блоками smoke → позитив → негатив (с подзаголовками), а не перемешан?

## Прослеживаемость — используй REQ-ID как есть

Каждый тест-кейс/пункт чек-листа должен ссылаться на `REQ-XXX`, из которого он выведен (см. колонку "Требование" выше). Если требований с ID ещё нет — это сигнал вернуться на шаг назад к **requirements-writer**/**requirements-reviewer**, а не присваивать ID задним числом внутри этого скилла.

## Пример интеграции с автотестами (vinnie-tests: pytest + Allure)

Если проект уже использует pytest + Allure (как в вашем vinnie-tests), держи `TC-001` как `allure.id("TC-001")` или в `@allure.title()` над соответствующим тестом — тогда трассировка "требование → тест-кейс → автотест" не теряется при переходе от дизайна к коду:
```python
@allure.id("TC-001")
@allure.title("Неполный голосовой ввод запрашивает уточнение")
def test_incomplete_input_requests_clarification():
    ...
```
