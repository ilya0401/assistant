# Написание требований

## Зачем это отдельный шаг

Требования, написанные "по ходу дела" внутри задачи на разработку или тест-дизайн, обычно расплывчаты и не атомарны — два требования склеены в одном предложении, нет ID для ссылки, непонятно, кто и зачем это попросил. Отдельный шаг даёт на выходе артефакт, на который можно сослаться (`REQ-003`), который можно проверить отдельно (requirements-reviewer) и из которого можно вывести тесты (test-design) — без повторного объяснения контекста каждый раз.

## Когда НЕ использовать этот скилл

Если требования уже написаны и нужно оценить их качество — это **requirements-reviewer**, не этот скилл. Если требования готовы и нужны тесты — это **test-design**. Этот скилл отвечает только за первый черновик с нуля.

## Шаг 1 — изучи весь проект и покажи карту возможностей

Прежде чем писать требования, изучи проект **целиком** — даже если область кажется очевидной из разговора (разговор мог не затронуть что-то важное, или твоя память о нём неполна). Пройдись по структуре репозитория, прочитай `CLAUDE.md`/`README.md`, пробегись по коду — ровно настолько, чтобы понять верхнеуровнево, какие у системы есть основные функции. Это не глубокое изучение реализации — это карта, а не чертёж.

Выведи пользователю (в чат, не в файл) короткий список обнаруженных возможностей — одним пунктом на функцию. Это контрольная точка: пользователь должен подтвердить, что ты реально охватил всю функциональность, а не только то, что обсуждалось в разговоре. **Не переходи дальше без подтверждения** — если пользователь поправит список (что-то упущено или не относится к делу), обнови его и дождись подтверждения снова.

## Шаг 2 — определи область (scope) для требований

Используя подтверждённую карту из Шага 1, определи, что документировать:
- **Конкретная функция/модуль** — если пользователь просил требования по чему-то одному или явно выбрал пункт из карты.
- **Вся функциональность целиком** — если просили требования на весь проект; в этом случае лучше сделать отдельный REQ-файл на каждую крупную область (см. Шаг 6), а не сваливать всё в один документ.

Если после карты всё ещё неясно, что выбрать — спроси пользователя явно, не угадывай.

## Шаг 3 — собери контекст, не додумывай его

Прежде чем писать требования, тебе нужно понимать:
- Кто пользователь/актор и какая у него цель
- Что уже существует (есть ли код/прототип, из которого видно реальное поведение)
- Есть ли технологические ограничения (стек, производительность, совместимость)
- Есть ли уже похожие требования в проекте — почитай `CLAUDE.md`, `README.md`, existing docs, если они есть, вместо того чтобы спрашивать то, что уже написано

Если контекста объективно не хватает (неясно, что должна делать система в конкретном случае, или на сколько акторов это распространяется) — **спроси пользователя**, а не изобретай правдоподобно звучащее требование. Придуманное "как будто логичное" требование хуже отсутствующего — оно пройдёт самостоятельную проверку (`requirements-reviewer` не знает, что ты его выдумал), но будет не соответствовать реальной системе.

## Шаг 4 — структура

Раздели на:
- **Функциональные требования (FR)** — что система делает
- **Нефункциональные требования (NFR)** — производительность, надёжность, безопасность, usability, совместимость

Каждое требование:

| Поле | Зачем |
|---|---|
| **ID** | `REQ-<ОБЛАСТЬ>-NNN`, например `REQ-STT-001`. Без ID нечего будет прослеживать дальше по пайплайну |
| **Текст** | Одно атомарное утверждение в форме "Система должна/не должна ..." |
| **Источник** | Кто попросил / откуда взято (стейкхолдер, существующий код, документация) — без этого требование невозможно будет верифицировать позже |
| **Приоритет** | Must / Should / Could (MoSCoW) или High/Medium/Low — спроси пользователя, если неочевидно из контекста |

## Шаг 5 — атомарность с самого начала

Не жди проверки скиллом requirements-reviewer, чтобы разбить составное требование — делай это сразу:

**Плохо (два требования в одном):**
> Система должна распознавать голосовую команду и сохранять запись в базу данных в течение 2 секунд.

**Хорошо (разделено):**
> `REQ-STT-001`: Система должна распознавать голосовую команду на русском языке.
> `REQ-PERF-001`: Система должна сохранять распознанную запись в базу данных не позднее чем через 2 секунды после завершения распознавания.

## Шаг 6 — сохрани в правильном месте

Требования — это артефакт продукта, а не тестового репозитория. Даже если ты сейчас запущен внутри `vinnie-tests`, сохраняй результат в:

```
vinnie-assistant/requirements/<kebab-case-слаг-фичи>.md
```

Один файл на фичу/область, не один общий файл на все требования проекта — так проще находить и точечно обновлять нужное. Например, для голосового логирования рабочего времени — `requirements/voice-command-logging.md`.

Перед тем как создавать новый файл — проверь, нет ли уже файла с таким же или близким слагом в `vinnie-assistant/requirements/`. Если есть — скорее всего, нужно дополнить существующие требования, а не плодить дубликат.

## Пример (на базе vinnie — voice work-time logger)

Вход: "Хочу, чтобы можно было сказать в микрофон что и сколько времени делал, и чтобы оно само разобралось и сохранило"

Выход:
```
REQ-STT-001 [Must] Система должна принимать аудио с микрофона браузера и передавать его на транскрипцию.
  Источник: голосовое описание пользователя

REQ-PARSE-001 [Must] Система должна извлекать из транскрипта номер задачи, затраченное время, дату и описание.
  Источник: голосовое описание пользователя

REQ-PARSE-002 [Must] Если хотя бы одно обязательное поле не извлечено, система должна запросить уточнение у пользователя, а не сохранять неполную запись.
  Источник: выведено из требования на полноту данных — уточни у пользователя, ожидался ли именно такой сценарий

REQ-STORE-001 [Must] Система должна сохранять извлечённую запись в Postgres.
  Источник: голосовое описание пользователя
```
Обрати внимание на `REQ-PARSE-002` — это требование, которого пользователь явно не произносил, но оно логически следует и помечено как "выведено", а не "сказано" — это честно и позволит requirements-reviewer и самому пользователю заметить, если вывод неверный.

## Перед тем как отдать черновик — самопроверка

- У каждого требования есть ID и указан источник?
- Нет ли предложения с союзом "и", склеивающим два требования в одно?
- Требования, выведенные логически, а не услышанные от пользователя — явно помечены "выведено"?
- Расставлен приоритет (Must/Should/Could), а не оставлен пустым "на потом"?

Если что-то из этого не так — поправь сейчас, а не рассчитывай, что requirements-reviewer это подхватит за тебя.

## Передача дальше

После черновика явно предложи пользователю прогнать результат через **requirements-reviewer** — не проверяй качество требований в рамках этого скилла, это отдельная ответственность с собственными критериями.
