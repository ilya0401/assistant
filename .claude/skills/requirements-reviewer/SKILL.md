# Проверка требований

## Когда НЕ использовать этот скилл

Если требований ещё нет — это **requirements-writer**, не этот скилл. Если требования уже проверены и нужны тесты — это **test-design**. ISTQB называет этот процесс "статическим тестированием" (review без выполнения кода/системы) — полезный термин, если нужно объяснить стейкхолдеру, зачем этот шаг вообще нужен до того, как что-то запущено.

Требования для vinnie хранятся в `vinnie-assistant/requirements/<слаг-фичи>.md` (см. requirements-writer). Если пользователь не прислал текст требований напрямую, а только назвал фичу — сначала поищи соответствующий файл там, прежде чем просить прислать требования вручную.

## Почему это два разных уровня проверки

Важный нюанс из стандарта ISO/IEC/IEEE 29148: часть характеристик — свойства **одного** требования (можно проверить его в изоляции), а часть — свойства **набора требований целиком** (бессмысленно спрашивать "это одно требование полное?" — полнота определяется относительно всего набора). Смешивать эти уровни — частая ошибка, которая превращает ревью в нечёткое "вроде норм". Раздели проверку на два прохода.

## Проход 1 — каждое требование по отдельности

Для каждого `REQ-XXX` проверь:

| Критерий | Вопрос, который себе задаёшь | Пример нарушения |
|---|---|---|
| **Недвусмысленность** | Поймут ли два разных читателя это требование одинаково? Нет ли слов типа "быстро", "удобно", "нормально" без числа/критерия? | "Система должна быстро отвечать" — быстро это сколько? |
| **Атомарность** | Это одно утверждение или несколько склеены союзом "и"/запятой? | "Должна распознавать речь и сохранять в БД" — это два требования |
| **Выполнимость** | Реализуемо ли это в рамках заявленного стека/сроков/бюджета, а не только теоретически? | "Распознавание речи без единой ошибки" — не достижимо технологически |
| **Проверяемость** | Можно ли придумать тест, который однозначно скажет "выполнено/не выполнено"? Если критерий успеха нельзя измерить или понаблюдать — требование непроверяемо | "Интерфейс должен быть интуитивным" — как это протестировать? |
| **Корректность** | Действительно ли это то, что нужно системе/пользователю, а не домысел или устаревшее поведение | Сверь с источником требования (его обязательно указывает requirements-writer) |

Для каждого нарушения — **не просто скажи "плохо"**, предложи переформулировку. Diagnosis без prescription бесполезен тому, кто будет это исправлять.

Пример разбора:
```
REQ-UI-004: Форма должна быстро загружаться и красиво выглядеть.

✗ Недвусмысленность: "быстро" и "красиво" не измеримы
✗ Атомарность: это два требования (производительность + визуальный дизайн)
✓ Выполнимость: ок, как только появятся числа
✗ Проверяемость: нельзя написать тест на "красиво"

Предлагаемая правка:
  REQ-UI-004 [Must] Форма должна полностью загружаться не более чем за 1.5 секунды на 4G-соединении.
  REQ-UI-005 [Should] Форма должна соответствовать дизайн-системе проекта (ссылка на Figma/гайдлайн).
```

## Проход 2 — набор требований целиком

| Критерий | Как проверяешь |
|---|---|
| **Полнота** | Пройдись по acceptance-критериям/пользовательским сценариям источника — есть ли сценарий, для которого нет ни одного требования? Особое внимание негативным и граничным сценариям — их обычно забывают первыми |
| **Непротиворечивость** | Есть ли пара требований, которые логически не могут выполняться одновременно? (например, REQ-A говорит "всегда сохранять черновик", REQ-B — "никогда не сохранять неполные данные") |
| **Прослеживаемость** | У каждого требования есть ID и указан источник (см. requirements-writer)? Без этого набор нельзя прослеживать ни назад (откуда взялось), ни вперёд (в тест-кейсы) |

Прослеживаемость здесь — это не отдельная метрика качества текста, а проверка **инфраструктуры** набора: если ID и источник на месте у каждого требования, прослеживаемость набора в порядке автоматически.

## Формат вывода

Таблица по каждому требованию (проход 1) + отдельный раздел "Выводы по набору" (проход 2):

```markdown
## Проход 1 — требования по отдельности
| ID | Недвусм. | Атомарн. | Выполн. | Провер. | Коррект. | Проблема | Предложенная правка |
|----|----------|----------|---------|---------|----------|----------|---------------------|
| REQ-UI-004 | ✗ | ✗ | ✓ | ✗ | ✓ | ... | ... |

## Проход 2 — набор целиком
- **Полнота**: не покрыт сценарий "пользователь отменил запись на середине" — нет соответствующего REQ
- **Непротиворечивость**: конфликтов не найдено / найдено между REQ-X и REQ-Y: ...
- **Прослеживаемость**: 2 требования без указанного источника (REQ-PARSE-003, REQ-STORE-002)
```

## Перед тем как отдать результат — самопроверка

- Оба прохода (по требованию и по набору) реально сделаны, а не только один?
- У каждой находки есть конкретная предложенная правка, а не только диагноз?
- Находки по набору (полнота/непротиворечивость) не перепутаны с находками по отдельному требованию?
- Если находок вообще нет — перепроверь себя: полное отсутствие проблем в реальном наборе требований редкость, возможно пропущен негативный/граничный сценарий

## Передача дальше

Когда ревью закончено и критичные находки исправлены — требования готовы для **test-design**. Не делай тест-дизайн в рамках этого скилла — его критерии (приоритизация, техники тест-дизайна) не пересекаются с критериями качества требований.
